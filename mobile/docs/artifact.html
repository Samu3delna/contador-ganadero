01 / PRODUCTO Y DECISIONES

Hecha para el trabajo de la finca.

El MVP reúne balance financiero, facturas, movimientos manuales, inventario y consulta tributaria. Los cálculos fiscales y las autorizaciones permanecen en el backend.

Decisiones confirmadas

  • mobile/ dentro del monorepo existente. Expo managed workflow y Expo Router.
  • Dirección visual 1: balance como foco, verde bosque, azul de marca, tipografías Outfit e Inter y navegación de cuatro pestañas.
  • SQLCipher por usuario y tenant, con desbloqueo del dispositivo. Sin bloqueo seguro no se habilita persistencia offline.
  • Access token en memoria; refresh token exclusivamente en SecureStore. Sin cookies de navegador en móvil.
  • Escrituras con conexión. No hay cola de sincronización ni OCR de fotografías.

El balance usa el período fiscal que devuelve la API. Se evitó rotular un acumulado anual como si fuera un monto mensual.

03 / AUTENTICACIÓN Y CACHÉ

La sesión viaja segura.

  1. Ingreso: login o registro → MFA cuando aplica → access en memoria y refresh en SecureStore.
  2. Renovación: un 401 comparte una promesa de refresh con las solicitudes simultáneas; se guarda el token rotado y cada solicitud se reintenta como máximo una vez.
  3. Revocación: el servidor invalida el token anterior y detecta reúso de familia. Credenciales revocadas provocan limpieza local.
  4. Restauración online: desbloqueo local → refresh → perfil validado por API.
  5. Restauración offline: desbloqueo → identidad protegida → plazo de siete días → último dashboard y páginas de facturas descargadas.
  6. Salida: revocación remota si hay red → invalidación de respuestas pendientes → limpieza de Query, refresh, clave y base cifrada.

Las operaciones de credenciales y vault se serializan para evitar que una respuesta tardía restaure una sesión cerrada. Al pasar a segundo plano se bloquea la UI, se cancelan consultas y se cierra el vault.

# Contrato móvil

Base: /api/mobile/auth. JSON; Cache-Control: no-store; sin Set-Cookie.
El cliente no acepta ni envía tenantId arbitrario.

| POST | Solicitud | Resultado |
|---|---|---|
| /login | email, password; opcional totpCode o backupCode heredado | Sesión o desafío |
| /registro | nombre, email, password, nombreFinca opcional, aceptaTerminos:true | 201 + sesión |
| /mfa/verify | mfaToken y totpCode (6 dígitos) o backupCode | Sesión |
| /refresh | refreshToken | Tokens nuevos |
| /logout | refreshToken | mensaje |

Sesión: {accessToken, refreshToken, expiresIn, user}.
Desafío: {mfaRequired:true, mfaToken, mensaje}; no entrega access ni refresh.
Refresh: {accessToken, refreshToken, expiresIn}; luego GET /api/auth/perfil para identidad actual.
expiresIn expresa segundos restantes del access token firmado, no una constante desconectada de JWT_EXPIRE.

Claims compartidos: id, tenantId, rol, tokenVersion, mfaVerifiedAt, iss y aud.
Refresh agrega type:refresh, jti y familyId. La base guarda hash del jti.
La familia se rota con compare-and-set; el token anterior deja de servir. El refresh rechaza cambios de tenant en la identidad de base de datos.
Los límites generales y específicos de auth se conservan.

Operaciones existentes con bearer:
- GET /api/auth/perfil
- POST /api/auth/logout-all
- POST /api/auth/forgot-password (público, respuesta no enumerante)
- GET /api/dashboard/resumen
- GET /api/facturas?page=1&limit=20&estado=revision
- GET /api/facturas/:id, /:id/xml, /:id/pdf
- POST /api/facturas/upload, multipart campo archivoXML, máximo 2 MB
- POST /api/facturas/manual
- GET/POST /api/ingresos; DELETE /api/ingresos/:id
- GET /api/inventario y /resumen; POST /bovinos, /aves, /peces, /colmenas
- GET /api/impuestos/proyeccion
- GET /api/declaraciones y /api/declaraciones/:id

Errores conservan error/mensaje/codigo según middleware existente. El cliente normaliza el texto visible.
400 entrada inválida; 401 credenciales/sesión; 402 tenant suspendido; 403 permiso/suspensión; 423 bloqueo temporal; 429 límite; 503 indisponibilidad.
415 archivo no XML; el XML inválido devuelve 400. Carga manual: extensión .xml y MIME XML/octet-stream, límite de 2 MB y tenant derivado de la sesión incluso ante otro receptor dentro del XML.
Los errores de transporte no se interpretan como revocación definitiva.

Compatibilidad web: /api/auth conserva respuesta token y cookie httpOnly, path, sameSite y secure existentes.
No se cambian webhooks, CORS, configuración Hacienda, ONVO ni cálculos fiscales.

08 / RIESGOS Y PRÓXIMOS PASOS

Validación nativa y publicación en tiendas.

  1. API desplegada en Render y descarga Android publicada. Mantener staging para validar flujos completos con datos de prueba.
  2. Instalar development builds Android/iOS y probar los flujos contra staging: login, MFA, reinicio, revocación, XML, permisos y tenants.
  3. Comprobar SQLCipher real, bloqueo PIN/biometría, caducidad, segundo plano, temporales de archivos y borrado local.
  4. Revisar la UI nativa frente a la opción 1, fuentes ampliadas, teclado, contraste, TalkBack/VoiceOver y modo oscuro.
  5. Vincular cuenta/proyecto EAS, validar identificadores, firma, privacidad y requisitos de publicación. No se despliega automáticamente.

Sin conexión no es posible conocer una revocación remota. El límite de siete días usa el reloj local y requiere endurecimiento adicional frente a manipulación deliberada. Un cierre offline elimina el acceso local, pero la revocación del servidor necesita red.

Las operaciones avanzadas de inventario permanecen en la web. OCR, emisión Hacienda, D-150, ONVO Checkout, chat IA y escrituras offline están fuera de esta entrega.

ARQUITECTURA DE AUTENTICACIÓN

El frontend web actual conserva su comportamiento sin cambios:

- Access token en memoria.
- Refresh token en cookie httpOnly.
- Rutas web actuales sin regresiones.

Agrega un adaptador móvil compatible:

POST /api/mobile/auth/login
POST /api/mobile/auth/mfa/verify
POST /api/mobile/auth/refresh
POST /api/mobile/auth/logout

El adaptador móvil debe reutilizar la lógica existente de autenticación, rotación y revocación. No dupliques validaciones de contraseña, MFA, bloqueo, suspensión, tokenVersion ni detección de reúso.

Contrato móvil esperado:

- Login exitoso: accessToken, refreshToken, expiresIn y user.
- Login con MFA pendiente: mfaRequired, mfaToken y mensaje.
- Refresh exitoso: nuevo accessToken, nuevo refreshToken y expiresIn.
- Logout: revoca el refresh token enviado.
- El refresh token nunca se registra en logs.
- El refresh token nunca se guarda en AsyncStorage, localStorage ni variables globales.
- El access token permanece únicamente en memoria.
- El refresh token se guarda exclusivamente con expo-secure-store.
- La rotación debe invalidar el token anterior.
- La reutilización de un token rotado debe revocar la familia completa.

Los tokens deben conservar tenantId, rol, tokenVersion, issuer y audience compatibles con protegerRuta.

La app nunca debe enviar tenantId arbitrario. El tenant siempre debe derivarse del token y de la base de datos.

Implementa un cliente Axios con:

- Base URL configurable.
- Header Authorization Bearer.
- Timeout razonable.
- Interceptor de respuesta 401.
- Una sola promesa de refresh simultánea.
- Reintento máximo de una solicitud.
- Logout local si falla el refresh.
- Mensajes de error en español.

## Adaptaciones de implementación

- SQLCipher almacena snapshots seleccionados; no se usa el persister AsyncStorage recomendado porque los datos financieros son sensibles. AsyncStorage conserva únicamente la preferencia de tema.
- Se agregó registro en /api/mobile/auth/registro; recuperación y logout global reutilizan sus rutas existentes.
- Expo SDK 58 requiere Node >=22.13 para mobile; se recomienda Node 24.13+ sin cambiar el mínimo histórico del frontend.
- Carpetas vacías src/config y src/features no se añaden: configuración en app.config.ts y funciones agrupadas en src/api y app.
- Fallos de refresh por credencial revocada cierran sesión; un fallo de conectividad puede conservar el vault vigente para lectura offline desbloqueada.
- Las pruebas de dispositivo y revisión visual nativa se declaran pendientes si el entorno no permite ejecutarlas. El artifact documenta evidencia real, no una certificación de producción.
